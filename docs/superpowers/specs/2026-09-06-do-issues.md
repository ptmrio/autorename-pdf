## #18: elevate only context-menu registry operations

**Boundary alternatives:** (A) a registry-only invocation mode in the existing `setup.ps1`; (B) a separate elevated helper script; (C) an inline elevated command containing registry code. **Lock A:** reuse `Add-RegistryEntries` and `Remove-RegistryEntries`, avoid a new packaged file and duplicated command-string logic.

The normal interactive setup process remains unelevated through config creation, prompts, OCR installation, model downloads, and OCR removal. Eliminate blanket startup `RunAs` and the unconditional administrator banner. Keep existing portable/standalone EXE discovery and existing HKLM locations for PDF, directory, and directory-background menus.

The same script exposes an internal `-ContextMenuAction Install|Uninstall` mode, with an absolute `-ExePath` for installation. This mode requires an elevated token, validates its action and installation EXE path, executes only the corresponding registry function, and exits with 0 for success or nonzero for failure. Dispatch it before the interactive routine; it must never copy config, prompt for OCR, install/remove OCR, or reach the closing `Read-Host`.

Only an affirmative context-menu install/remove choice launches that mode through `Start-Process powershell.exe -Verb RunAs`, using a quoted absolute script path and arguments, `-NoProfile`, `-ExecutionPolicy Bypass`, and `-Wait -PassThru`. The original process stays alive and resumes the menu after the child exits. Do not rely on the child's working directory or pass a fabricated user profile to an elevated OCR installer. Keep setup rooted at `$PSScriptRoot`. This registry helper needs no visible interactive window; request `-WindowStyle Hidden`.

Cancellation, launch failure, or registry failure must be reported for the context-menu action without falsely marking it installed/removed, and must allow the original user to continue to OCR. Registry errors must reach the exit status; uninstalling an already-absent entry succeeds, but access errors do not. No registry rollback framework is required; operations remain safe to retry.

**Already-elevated launch alternatives:** (A) refuse interactive mode with a concise instruction to rerun normally; (B) add token/Explorer machinery to relaunch as the desktop user. **Lock A:** before any interactive-mode writes, explain that setup must be launched from normal PowerShell for per-user OCR. The explicit registry-only mode remains allowed. Never guess the intended user or install OCR under an administrator profile.

`Install-PaddleOCR` and OCR uninstall use the original user's `$env:LOCALAPPDATA\autorename-pdf`; model downloads use that user's normal profile/cache. Remove the administrator-created-model `icacls` workaround. Preserve package pins, CPU/GPU selection and fallback, and existing installation mechanics. Make the entire `setup.ps1` ASCII-only, including decorative comments, and correct its launch guidance. Add a short corresponding launch/elevation clarification in `README.md`.

**Cosmetic cwd alternatives:** (A) retain current context-menu command strings; (B) prepend quoted `cd /d` to the install directory. **Lock A:** omit the optional Google Drive cosmetic change to keep this PR focused and avoid extra quoting risk.

## #19 temperature half: verify, do not re-implement

Inspection found no remaining temperature leak. `_ai_processing.py:build_provider_create_kwargs`, `_get_openai_client`, `_get_anthropic_client`, and all three text/image/combined routes already implement native parsing. The branch omits temperature for **all** native OpenAI requests, including Luna, and all Anthropic requests. This differs from the issue's older unconditional-temperature behavior.

Preserve the following existing contract; no `_ai_processing.py` production edit is expected:

| Provider | Native request contract |
|---|---|
| Anthropic | `messages.parse`, `output_format=DocumentMetadata`, `max_tokens=1024`; no `temperature` or OpenAI reasoning kwargs. |
| OpenAI Luna / `gpt-5.6-*` | `responses.parse`, `text_format=DocumentMetadata`, `store=False`, `reasoning={"effort": "none"}`; no `temperature`. |
| Other OpenAI models | Same native parse; omit both `temperature` and the explicit reasoning override. |
| Gemini / xAI / Ollama | Preserve instructor TOOLS / TOOLS / JSON respectively and configured temperature. |

Retain client authentication, OpenAI custom base URL, and SDK retry behavior. Keep the existing model-family check; no generalized capability registry or model expansion in this slice.

Official practices, **accessed 2026-09-06**:

- Anthropic's [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) documents Python `messages.parse` with `output_format` and parsed results. Its [Messages API](https://platform.claude.com/docs/en/api/messages/create) marks temperature deprecated for models after Opus 4.6 and rejects values other than the compatibility value 1.0. Project lock: send no temperature to current Claude models, retaining omission for the whole Anthropic path.
- OpenAI's [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) documents native `responses.parse` with Pydantic. [Reasoning](https://developers.openai.com/api/docs/guides/reasoning) makes effort support model-dependent; the [Luna model page](https://developers.openai.com/api/docs/models/gpt-5.6-luna) lists `none`. Project lock: explicitly send `none` only for Luna / `gpt-5.6-*`, omit temperature for those models, and preserve omission for other OpenAI models. This conservative project rule is not a claim that only those models support `none` or that every OpenAI model rejects temperature.

Verify `tests/test_ai_processing.py::TestBuildProviderCreateKwargs`, `TestNativeStructuredExtract`, and `TestNativeClientMaxRetries`. Existing text-call tests assert omission; extend existing image and combined-call tests only where needed to assert no temperature and the correct reasoning override. Exercise a nonzero configured temperature so omission cannot be mistaken for passing zero. Keep non-Luna `gpt-5` coverage and check a non-Luna `gpt-5.6-*` name against the existing family rule. Do not duplicate the provider implementation.
